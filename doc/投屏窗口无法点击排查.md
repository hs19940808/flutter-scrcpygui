# 投屏窗口无法点击排查

排查日期：2026-10-19。对象为 Windows 上通过 Wi-Fi 连接的
MEIZU 20 Pro（Android 16），Scrcpy 4.1，汽车之家虚拟显示窗口。

## 已确认的原因

本次现场是 Android 虚拟显示因闲置进入休眠，导致输入窗口失去焦点。
Windows 投屏进程仍处理窗口消息并保留最后一帧，因此看起来像窗口卡住。

| 现场检查 | 结果 |
| --- | --- |
| Windows 主程序 / 投屏进程 | 均为 `Responding=True` |
| ADB | 设备在线，能够正常执行诊断命令 |
| 原投屏 | `displayId=25`，`state OFF` |
| Android 电源状态 | `mWakefulness=Dozing` |
| 充电状态 | `mIsPowered=false`，`mPlugType=0`，`mStayOn=false` |
| 休眠设置 | `screen_off_timeout=60000`，即 60 秒 |
| 输入分发 | `FocusedWindows: <none>`，显示 25 的焦点请求为 `NO_WINDOW` |
| 原启动参数 | `--new-display --stay-awake --keyboard=uhid`，没有 `--keep-active` |

`--stay-awake` 只在设备接电时防止休眠，不能覆盖本次未充电的 Wi-Fi 场景。
Scrcpy 4.0 起提供 `--keep-active`，周期性向目标显示报告用户活动，
无需修改手机全局休眠设置，也不依赖接电。

依据：[设备选项说明](https://github.com/Genymobile/scrcpy/blob/v4.1/doc/device.md#keep-active)、
[4.0 发布说明](https://github.com/Genymobile/scrcpy/releases/tag/v4.0)、
[官方同类问题 #6787](https://github.com/Genymobile/scrcpy/issues/6787)。

## 现场验证及恢复

1. 对原窗口点击“价格低”，排序与画面没有变化，复现无法点击。
2. 执行 `adb shell input -d 25 keyevent KEYCODE_WAKEUP`，主屏被唤醒，
   虚拟显示仍为 `OFF`、无焦点；Scrcpy 右键也未恢复该显示。
3. 保留原进程，建立带 `--keep-active` 的临时设置应用投屏，显示编号为 26。
   它与原显示同属电源显示组 1。已有显示组休眠时，新窗口同样为 `OFF`，
   说明 `--keep-active` 不能直接唤醒已经休眠的显示组。
4. 通过临时诊断程序检查本机 Android 电源接口，确认存在
   `wakeUpWithDisplayId(long,int,String,String,int)`，对显示 25 定向调用。
   14:58:42，原显示与临时显示均恢复 `ON`，原窗口重新刷新。
5. 在原窗口点击“价格低”，选中标记与列表顺序发生变化，确认输入恢复。
6. 保持原窗口不操作超过两分钟，15:00:59 检查显示 25、26 仍为 `ON`，
   未接电状态不变，显示组的最后活动时间由保活线程持续更新。
   随后再次点击“默认排序”成功，并恢复原排序选项。

上述验证恢复了原投屏进程，没有重启汽车之家或修改手机休眠时长。
定向唤醒使用的是该设备实际提供的内部接口，不能假定所有 Android 版本
都有相同签名。诊断程序不属于产品运行时依赖。

## 源码修复范围

`lib/utils/scrcpy_command.dart` 在生成启动参数时，根据所选 Scrcpy 版本：

- 4.0 及以上：虚拟显示自动追加 `--keep-active`。
- 4.0 及以上：用户启用“保持唤醒”时，也追加 `--keep-active`，覆盖未接电场景。
- 保留原有 `--stay-awake` 参数及配置结构。
- 3.x 不自动加入不支持的参数，避免内置 3.2 启动失败。
- 用户已在附加参数中填写 `--keep-active` 时不重复追加。
- 普通投屏未启用保持唤醒时，保留原休眠行为。

这项修改用于预防新会话再次因闲置休眠；运行中的旧进程不会自动获得新参数。
源码更新与已安装版本的替换是两个步骤，已安装程序必须更新并重启相关投屏
才能使用新参数。旧版 Scrcpy 3.x 不在本次保活修复覆盖范围内。

## 另一项代码风险

`CommandRunner.startScrcpyCommand()` 返回子进程后，只有打开 `LogScreen`
才订阅 `stdout` / `stderr`。正常应用启动不进入该页面；离开日志页后还会取消订阅。
当子进程输出超过管道容量时，未持续读取的输出可能阻塞子进程。

这是独立风险，本次恢复原进程后点击成功，没有证据证明现场发生了管道写满，
因此本次没有把它当作已经确认的根因，也没有扩大源码修改范围。
后续修复应由实例创建时持续消费输出，并把日志页面改为读取有容量限制的缓存。

依据：[Dart Process.stdout 文档](https://api.dart.dev/dart-io/Process/stdout.html)。
